# PayPal 跨站支付跳转体验优化方案

## 1. 目的与适用范围

本文分析 PaypalA / PaypalB 双站支付流程中买家点击步骤偏多的问题，给出可落地的优化方案与实施要点。

适用前提：

- A 站已安装 PaypalA 插件，B 站已安装 PaypalB 插件，跨站桥接已跑通；
- B 站 PayPal 收款账号使用 REST API 模式（`mode = automatic`）；
- 钱包（wallet）与信用卡（card）两种付款方式的现状分别对待。

本文只做方案分析与设计，不包含代码改动。文中引用的行为均以当前代码为准。

## 2. 现状：买家需要点击 3 次

| 步骤 | 买家动作 | 技术实质 | 代码位置 |
|---|---|---|---|
| 1 | A 站点「前往 B 站使用 PayPal 钱包付款」 | 表单 POST → 创建 B 站会话与 PayPal Order → 302 到 B 站结账页 | `PaypalAController::start()` |
| 2 | B 站点 PayPal 按钮 | `paypal.Buttons` 的 `createOrder` 返回已建 order id，点击后打开授权弹窗 | `Views/checkout/wallet.blade.php` |
| 3 | PayPal 弹窗内登录并确认 | PayPal 域内完成授权 → `onApprove` → 调用 B 站 capture 接口 | 同上 |

其中第 3 步是 PayPal 域内的必要操作，任何方案都无法省略。**可优化的是第 1、2 步之间的冗余。**

## 3. 为什么「自动触发 PayPal 按钮」不可行

原始设想是：买家在 A 站点一次，跳到 B 站后由脚本自动触发 PayPal 按钮，直接弹出登录界面。这条路走不通。

PayPal Buttons 被点击后需要调用 `window.open` 打开授权弹窗。**浏览器只允许在真实用户手势（user gesture）的同步调用栈内打开弹窗**。页面加载完成后由脚本调用 `.click()` 或以其他方式程序化触发，已经脱离用户手势上下文，弹窗会被拦截器阻止。

实际效果会是：买家看到空白区域或浏览器的「已阻止弹出式窗口」提示条，需要手动允许弹窗后再点一次。**这比现状多一步，且是转化流失最严重的一步。**

这是浏览器安全模型的限制，不是实现技巧问题，无法绕过。

## 4. 可行路径：用 approval_url 整页跳转

### 4.1 关键事实

B 站创建 PayPal Order 时，PayPal 返回的买家授权地址**已经被保存**：

```php
// PaypalBTransactionService::storeCreatedOrder()
'approval_url' => $approvalUrl,
```

回跳链路也**已经完整实现**：

- 建单时传给 PayPal 的 `return_url` 指向 `PaypalBController::returnFromPaypal()`，该方法已实现 capture；
- `cancel_url` 指向 `PaypalBController::cancel()`，已处理买家放弃；
- capture 完成后 `markCompleted()` 触发回调 A 站并生成 B 站订单。

也就是说，只要让 B 站在钱包方式下直接 302 到 `approval_url`，「跳 PayPal → 登录 → 授权 → 回跳 capture → 回 A 站」整条链路即可打通。**这条路径不需要新写业务逻辑，只需要增加一个分支和一个开关。**

### 4.2 优化后的链路

| 步骤 | 买家动作 | 技术实质 |
|---|---|---|
| 1 | A 站点 PayPal 按钮 | 创建会话 → 302 到 B 站 → B 站 302 到 PayPal |
| 2 | PayPal 页面内登录并确认付款 | 授权后 PayPal 跳回 B 站，B 站 capture 并回跳 A 站 |

买家只需点击 1 次按钮。整页跳转不受弹窗拦截影响，移动端体验优于弹窗方案。

## 5. 方案对比

| 方案 | 买家点击数 | 改动量 | 主要风险 | 结论 |
|---|---|---|---|---|
| A. approval_url 直通 | 1 | 小，链路已存在 | 合规披露需迁移到 A 站 | **推荐** |
| B. 自动 click SDK 按钮 | 1~2 | 小 | 弹窗被浏览器拦截，不可靠 | 否决 |
| C. B 站页面优化（按钮提到首屏） | 3 | 极小 | 无 | 可作为过渡 |
| D. A 站直接渲染 PayPal 按钮 | 1 | 中 | 破坏 A/B 站隔离 | 不建议 |

### 5.1 关于方案 D 的说明

方案 D 技术上可行：PayPal client-id 是公开值，A 站可异步向 B 站建单、拿到 `paypal_order_id` 后在 A 站页面渲染 PayPal 按钮，由于是真实用户手势，弹窗不会被拦截，体验最好。

但该方案会使 PayPal 交易发生在 A 站域名下，A 站域名需要登记进 PayPal 应用配置。当前 A/B 双站架构（配合 CyberCloak 商品映射）的前提就是让 PayPal 只接触 B 站。方案 D 会取消这一前提，因此不建议采用。

## 6. 推荐方案（A）的实施要点

### 6.1 钱包直通，卡片留页

信用卡付款走 PayPal CardFields 托管字段，买家必须在 B 站页面内输入卡号，不存在可跳转的 `approval_url`。

因此优化范围仅限钱包方式，**B 站结账页仍需保留**，用于卡片付款和直通失败时的兜底。

### 6.2 合规披露迁移到 A 站

这是方案 A 唯一的实质代价。

当前 B 站结账页（`Views/checkout/summary.blade.php`）承担着收款主体披露职责：商户名称、退款政策、隐私政策、交易条款。直通之后买家不再看到该页面，PayPal 授权页只会显示建单时传入的 `brand_name`。

建议做法：**在 A 站支付页展示 B 站商户名与政策链接**。A 站支付页是买家本来就会停留的页面，在此披露具有实际意义。

不建议做法：使用「中转页 + 自动跳转」。买家实际无法阅读一个 0.3 秒闪过的页面，等同于未披露，还多一次页面加载。

### 6.3 按开关切换，不做硬替换

建议在 PaypalB 插件配置中增加「钱包付款方式」选项：直通 PayPal / 站内按钮页。

理由：直通模式一旦在 PayPal 侧出现问题（授权地址失效、地区限制、账号能力变更），需要能够立即切回现有的 SDK 按钮页面兜底，而不是等待代码发布。

### 6.4 A 站按钮的品牌合规

A 站按钮改为 PayPal 视觉样式时，应使用 PayPal 官方品牌素材包提供的 logo 与配色，不要自行设计形状与文案。

需要注意：PayPal 品牌指南要求使用 SDK 渲染的官方按钮，自绘按钮属于灰色地带。A 站不持有也不应持有 PayPal client-id，无法渲染官方按钮，因此只能采用视觉近似方案。此处存在品牌规范上的取舍，需业务方知悉。

## 7. 风险与待验证事项

### 7.1 approval_url 复用行为（必须实测）

`approval_url` 是一次性的 PayPal checkout 链接。以下场景的实际表现**尚未验证**：

- 买家在 PayPal 页面中途返回、刷新，或从浏览器历史重新进入 A 站再次发起付款；
- 此时 A 站 `reserveTransaction()` 会复用同一会话，B 站将再次 302 到同一个 `approval_url`；
- 若买家此前已在 PayPal 侧完成批准但 capture 未完成，可能出现异常。

现有 `recoverCompletedCapture()` 对 capture 幂等场景有兜底，但直通模式下的完整表现需要在 PayPal 沙盒中逐一验证。

### 7.2 买家取消路径

PayPal 授权页的「取消并返回」会跳转到 `cancel_url`，由 `PaypalBController::cancel()` 处理并回调 A 站。该路径已实现，但在直通模式下的实际跳转需一并验证。

### 7.3 会话有效期

PayPal Order 的有效期长于跨站会话有效期（默认 30 分钟）。买家在 PayPal 页面停留超过会话有效期后再确认付款，回跳 capture 时会因 `assertActive()` 判定过期而失败。该行为在现有方案中同样存在，直通模式下因买家停留在外部页面，触发概率可能上升。

## 8. 实施清单

无新增数据表，预计 4~6 处改动：

| 改动点 | 说明 |
|---|---|
| `PaypalBController::checkout()` | 钱包方式且开关开启时，302 到 `approval_url` |
| `PaypalBConfiguration` | 新增钱包付款方式开关字段 |
| PaypalB 后台配置页 | 开关的表单项与说明 |
| A 站支付页 | 按钮改 PayPal 视觉样式 |
| A 站支付页 | 增加 B 站商户名与政策链接展示 |
| 商户信息传递 | 现有 `statusPayload()` 不含商户名与政策链接，需补充字段，或在 A 站插件配置中单独填写 |

工作量预估：半天到一天。主要时间消耗在 PayPal 沙盒中验证第 7 节的边界场景，而非编码。

## 9. 验证清单

上线前需在 PayPal 沙盒中确认：

- [ ] 钱包直通：A 站点击后直达 PayPal 登录页，无中间页面；
- [ ] 授权完成后正确回跳 B 站并 capture，A 站订单转为已支付；
- [ ] B 站影子订单正常生成；
- [ ] 在 PayPal 页面点击取消，正确回到 A 站且订单仍可重新付款；
- [ ] 同一订单重复发起付款，不产生第二个 PayPal Order；
- [ ] 会话过期后再确认付款，错误提示正确且订单未被错误标记；
- [ ] 关闭开关后，回退到站内按钮页且功能正常；
- [ ] 信用卡付款流程不受影响；
- [ ] 多语言：切换语言后 A 站按钮文案与 PayPal 页面语言一致。

## 10. 回滚方案

方案 A 的全部行为由配置开关控制。出现问题时：

1. 在 B 站后台将「钱包付款方式」切回「站内按钮页」；
2. 执行 `php artisan cache:clear`；
3. 流程立即回到当前的三步链路，无需回滚代码或数据。

已经跳转到 PayPal 但尚未完成的会话不受开关影响，仍会按原 `return_url` 回跳并正常 capture。
